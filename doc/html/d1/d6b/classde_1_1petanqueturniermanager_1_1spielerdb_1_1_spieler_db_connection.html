Ausführliche Beschreibung

Implementierung: SQLite via xerial sqlite-jdbc.

Pfad: ~/.petanqueturniermanager/spielerdb/spieler.sqlite3. SQLite-Filelocking erlaubt mehrere Prozesse parallel auf derselben Datei — mit aktiviertem WAL-Mode sogar concurrent readers während eines Writers. Damit ist der frühere HSQLDB-Server-Mode-Workaround obsolet.

Schema-Erstellung läuft idempotent über CREATE TABLE IF NOT EXISTS. Im Plugin-Betrieb wird eine Singleton-Connection gehalten; Tests greifen über fuerJdbcUrl(String) mit jdbc:sqlite::memory: auf isolierte In-Memory-DBs zu.

◆ initialisiereVerbindung()

void de.petanqueturniermanager.spielerdb.SpielerDbConnection.initialisiereVerbindung ( Connection conn) throws SQLException
staticprivate

Reihenfolge wichtig:

  • foreign_keys = ON muss pro Connection gesetzt werden, SQLite-Default ist OFF.
  • journal_mode = WAL aktiviert Write-Ahead-Log → concurrent readers während eines Writers, ideal für mehrere LO-Prozesse. Persistent in der Datei, einmalige Aktivierung reicht eigentlich, schadet aber nicht beim erneuten Setzen.
  • synchronous = NORMAL ist die für WAL empfohlene Einstellung (gut genug für Stammdaten, deutlich schneller als FULL).
  • busy_timeout = 5000 lässt einen blockierten Writer bis zu 5 s auf den Lock warten, statt sofort SQLITE_BUSY zu werfen.

Für In-Memory-Tests (URL jdbc:sqlite::memory:) ist WAL ein No-Op, SQLite ignoriert den Mode dort gracefully.

◆ registriereJavaLower()

void de.petanqueturniermanager.spielerdb.SpielerDbConnection.registriereJavaLower ( Connection conn) throws SQLException
staticprivate

SQLites eingebautes LOWER() ist ASCII-only — LOWER('MÜLLER') bleibt 'MüLLER', sodass case-insensitive-Suchen über deutsche Umlaute fehlschlagen. Mit dieser UDF läuft das Lowercase über String#toLowerCase(Locale) mit Locale#ROOT und liefert echtes Unicode-Lowercase, identisch zur Java-seitigen Normalisierung in den Repository-Aufrufern.

◆ restoreVon()

synchronized void de.petanqueturniermanager.spielerdb.SpielerDbConnection.restoreVon ( Path quelle) throws SpielerDbException
static

Schließt die aktuelle Connection, sichert die alte Datei nach <db>.bak.<yyyyMMdd-HHmmss>, kopiert die Quelle an die DB-Stelle und öffnet die Connection neu.

Pre-Conditions: aktuelle DB ist file-basiert, quelle ist eine SQLite-Datei (Magic-Bytes geprüft). Bei Fehler im Kopier-/Open-Schritt wird das Backup zurückgespielt und die Connection wieder geöffnet.
